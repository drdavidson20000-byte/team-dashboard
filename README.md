# 영업기획관리실 대시보드 — 배포 가이드

Claude(Anthropic) 서버에 의존하지 않고, 무료 서비스(Firebase + GitHub Pages)만으로 크롬 브라우저에서
접속해 쓸 수 있는 팀용 웹앱입니다. 변호사 사건관리 대시보드와 동일한 구조(Firebase Authentication +
Firestore 보안 규칙)를 사용해서, 로그인 화면이 진짜로 데이터베이스 접근을 막아줍니다.

- 데이터 저장: **Firebase Firestore** (무료 Spark 플랜)
- 로그인 보호: **Firebase Authentication** (이메일/비밀번호, 팀 공용 계정 1개)
- 호스팅: **GitHub Pages** (무료 정적 호스팅)

현재 구현된 기능:

- **주간보고** 탭 → **영업기획팀 / 영업관리팀** 팀별 탭 → **3-layer 구조**
  (1차: 프로젝트, 예 GMCS project / 2차: 카테고리, 예 기획·대시보드 / 3차: 주차별 상세내용).
  **각 주는 완전히 독립된 기록입니다** — 분류/항목/상세설명이 모두 주 단위로 저장되므로,
  어느 한 주에서 내용을 추가하거나 고쳐도 다른 주의 기록에는 전혀 영향을 주지 않습니다.
  새로운 주로 이동하면 항상 빈 화면으로 시작하며, "지난 주 내용 가져오기" 버튼을 눌러야만
  그 시점의 지난 주 내용이 복사됩니다. 팀별 전체 기록을 주차별 시트로 나눠 엑셀로 내려받는
  기능도 있습니다.
- **지시사항** 탭 → 지시 날짜·이행예정 날짜·지시사항 내용·담당팀·담당자·진행상태를 표로
  관리합니다. 팀별로 탭이 나뉘지 않고 표 하나에서 전체를 보며, 담당팀은 필터링 가능한
  항목 중 하나입니다. 자세한 사용법은 아래 3단계를 참고하세요.
- **성과관리** 탭 → 올해 성과지표(평가 항목·전략 방향·목표·평가 기준·보조 지표 등)를
  정리한 표를 보여주는 **읽기 전용 참고용 화면**입니다. 열이 많아 한눈에 보기 어려울 때를
  위해 "산출식", "측정 방법", "평가 기준(4열)", "보조 지표(3열)" 버튼으로 원하는 열 묶음을
  숨기거나 다시 보이게 할 수 있습니다. 숨긴 상태는 이 브라우저에만 저장되어 새로고침해도
  유지되며, 다른 팀원의 화면에는 영향을 주지 않습니다. 각 열은 내용이 잘리지 않을 만큼
  적당한 너비로 고정되어 있고, 표 전체 폭이 화면보다 넓으면 (내용을 억지로 좁은 칸에
  구겨넣어 세로로 한없이 길어지는 대신) 표 영역을 좌우로 스크롤해서 나머지 열을 확인합니다.
  현재는 이 화면에 있는 값을 직접 고치는 편집 기능은 없고(내용이 바뀌면 이 파일들을 다시
  배포해야 합니다), 필요하시면 나중에 주간보고처럼 Firestore에 저장해서 화면에서 바로
  편집할 수 있게 확장할 수 있습니다.
- **식당** 탭 → 팀 구분 없이 전체가 함께 보는 **회사 주변 맛집 공유 메모장**입니다. "+
  식당 추가"로 식당명·분류(한식/중식/일식/아시안/양식/간편식/카페/주류/기타)·위치(방이/
  송리단/롯데몰/기타)·메모·작성자를 적고, 캡처한 화면을 그 자리에서 붙여넣기(Ctrl+V)하거나
  파일을 끌어다 놓아서 사진을 최대 4장까지 첨부할 수 있습니다(붙여넣은 사진은 브라우저에서
  자동으로 크기와 용량을 줄인 뒤 저장됩니다 — 아래 참고). 카드를 클릭해 편집·삭제할 수 있고,
  분류·위치·검색어로 필터링해서 원하는 식당만 모아볼 수 있습니다.

  **사진은 왜 압축해서 저장하나요?** 사진을 저장하는 가장 일반적인 방법은 Firebase Storage인데,
  2024년 정책 변경으로 Storage는 무료(Spark) 요금제에서는 아예 쓸 수 없고 유료(Blaze) 요금제로
  업그레이드(신용카드 등록)해야만 사용할 수 있게 되었습니다. 이 대시보드는 완전 무료 구성을
  유지하기 위해, 붙여넣은 사진을 브라우저에서 자동으로 작게 리사이즈·압축한 뒤 글 내용과 함께
  그대로 Firestore에 저장하는 방식을 택했습니다. 그 결과 식당 1건당 사진은 최대 4장까지,
  압축 후 사진 용량 합계가 약 900KB를 넘지 않도록 제한됩니다(Firestore 문서 1개당 저장 용량
  한도가 1MB이기 때문입니다). 이 정도면 화면에서 보기에는 충분한 화질이지만, 원본 그대로의
  고화질 사진을 다루고 싶다면 나중에 Blaze 요금제로 업그레이드하고 Firebase Storage를 연동하는
  방식으로 확장할 수 있습니다(말씀해주시면 도와드릴 수 있습니다).

## 1단계. Firebase 프로젝트 만들기

1. https://console.firebase.google.com 접속 후 구글 계정으로 로그인
2. **"프로젝트 추가"** 클릭 → 프로젝트 이름 입력 (예: `seegene-team-dashboard`) → 애널리틱스는 꺼도 무방 → 프로젝트 생성

### 1-1. Firestore Database 활성화
1. 왼쪽 메뉴 **빌드 > Firestore Database** 클릭 → **"데이터베이스 만들기"**
2. 위치는 `asia-northeast3 (서울)` 선택 (한국 기준 속도가 가장 빠름)
3. 보안 규칙은 **프로덕션 모드**로 선택하세요. (테스트 모드는 30일 후 규칙이 자동으로 "전체 차단"으로
   잠기는데, 아래 1-2단계를 건너뛴 채 넘어가면 어느 날 갑자기 접속이 안 되는 문제가 생길 수 있습니다.
   프로덕션 모드는 처음부터 기본이 "전체 차단"이라 1-2단계에서 규칙을 직접 넣어야만 열립니다.)

### 1-2. 보안 규칙 설정 (중요 — 반드시 진행)
1. Firestore Database 화면에서 **"규칙(Rules)"** 탭 클릭
2. 아래 내용(이 프로젝트의 `firestore.rules` 파일 내용)을 그대로 붙여넣고 **"게시(Publish)"**

```
rules_version = '2';
service cloud.firestore {
  match /databases/{database}/documents {
    match /layer1/{docId} {
      allow read, write: if request.auth != null;
    }
    match /layer2/{docId} {
      allow read, write: if request.auth != null;
    }
    match /layer3/{docId} {
      allow read, write: if request.auth != null;
    }
    match /directives/{docId} {
      allow read, write: if request.auth != null;
    }
    match /restaurants/{docId} {
      allow read, write: if request.auth != null;
    }
  }
}
```

이 규칙은 **로그인한 사용자만** 주간보고 데이터를 읽고 쓸 수 있게 막아줍니다. 이 단계를 건너뛰면
누구든 인터넷에서 데이터를 열람/수정할 수 있으니 꼭 설정하세요.

### 1-3. 로그인(Authentication) 설정
1. 왼쪽 메뉴 **빌드 > Authentication** → **"시작하기"**
2. **"Sign-in method"** 탭 → **"이메일/비밀번호"** 선택 → 사용 설정 → 저장
3. **"Users"** 탭 → **"사용자 추가"** → 팀에서 공용으로 쓸 이메일/비밀번호 입력 후 저장
   - 이 계정이 곧 대시보드 로그인 계정입니다. 팀원들에게 이 이메일/비밀번호를 공유하면 됩니다.
   - 필요하면 팀원별로 계정을 추가로 만들어도 됩니다 (Users 탭에서 "사용자 추가"를 반복).

### 1-4. 웹 앱 등록 & 설정값 복사
1. 프로젝트 설정(⚙️ 아이콘) > **"프로젝트 설정"** 클릭
2. 아래로 스크롤 → **"내 앱"** → `</>` (웹 앱 추가) 아이콘 클릭
3. 앱 닉네임 입력 (예: `team-dashboard-web`) → Firebase 호스팅은 체크하지 않아도 됨 → 앱 등록
4. 화면에 나오는 `firebaseConfig` 객체 값을 복사합니다. 예:

```js
const firebaseConfig = {
  apiKey: "AIzaSy....",
  authDomain: "seegene-team-dashboard-xxxx.firebaseapp.com",
  projectId: "seegene-team-dashboard-xxxx",
  storageBucket: "seegene-team-dashboard-xxxx.appspot.com",
  messagingSenderId: "1234567890",
  appId: "1:1234567890:web:abcdef123456"
};
```

5. 이 프로젝트 폴더의 **`firebase-config.js`** 파일을 열어 `YOUR_API_KEY` 등 자리표시자 값을
   위에서 복사한 실제 값으로 교체 후 저장합니다. (이 값은 비밀키가 아니라 앱 식별용 공개 설정이라
   GitHub에 그대로 올려도 안전합니다 — 실제 보호는 1-2단계의 보안 규칙과 1-3단계의 로그인이 담당합니다.)

## 2단계. GitHub 저장소 만들고 GitHub Pages로 배포

1. https://github.com 에서 계정이 없다면 무료로 가입
2. 우측 상단 **"+" > "New repository"** → 저장소 이름 입력 (예: `team-dashboard`) →
   **Public**으로 설정(GitHub Pages 무료 사용을 위해 Public 권장) → **Create repository**
3. 저장소 페이지에서 **"uploading an existing file"** 링크 클릭 (또는 "Add file > Upload files")
4. 이 폴더 안의 파일들을 전부 드래그해서 업로드:
   - `index.html`
   - `style.css`
   - `app.js`
   - `firebase-config.js` (실제 값으로 수정한 버전)
   - (참고용) `firestore.rules`, `README.md`
5. 하단에 커밋 메시지 입력 후 **"Commit changes"**

### 2-1. GitHub Pages 활성화
1. 저장소 상단 메뉴 **Settings > Pages** 이동
2. **"Build and deployment"** 의 Source를 **"Deploy from a branch"**로 선택
3. Branch를 `main` (또는 `master`), 폴더는 `/ (root)` 선택 후 **Save**
4. 1~2분 후 같은 화면 상단에 `https://<본인계정>.github.io/team-dashboard/` 형태의 주소가 생성됩니다.

### 2-2. Firebase에 배포 주소 등록 (승인된 도메인)
GitHub Pages 주소가 Firebase 로그인에서 차단되지 않도록 등록해야 합니다.
1. Firebase 콘솔 > Authentication > **Settings** 탭 > **"승인된 도메인(Authorized domains)"**
2. **"도메인 추가"** → `<본인계정>.github.io` 입력 후 추가

## 3단계. 접속 & 사용

1. 크롬에서 `https://<본인계정>.github.io/team-dashboard/` 접속
2. 1-3단계에서 만든 이메일/비밀번호로 로그인
3. **주간보고 탭** → 영업기획팀 / 영업관리팀 중 팀 선택
4. 화면은 표(엑셀 형태) 한 장으로 구성됩니다: **분류**(프로젝트) → **항목**(카테고리) →
   **금주**(이번 주 진행 내용) → **차주**(다음 주 계획) → **담당자** 순서로 이어집니다.
   같은 분류에 속한 항목들은 분류 셀이 세로로 병합되어 표시됩니다. 위 **+ 프로젝트 추가**로
   분류를 만들고, 분류 셀의 **+ 항목**으로 그 아래 항목(행)을 추가합니다. 금주/차주 칸은
   비어 있으면 "클릭해서 작성"이라고 뜨며, 클릭하면 바로 그 자리에서 입력 후 저장할 수
   있습니다. 담당자 칸은 클릭 없이 바로 이름을 입력하고 다른 곳을 클릭하거나 Enter를
   누르면 저장됩니다.
5. 상단 주차 이동(‹ ›)으로 지난 주 기록도 확인할 수 있습니다. **분류/항목/금주/차주/담당자
   모두 주차마다 완전히 별개의 데이터입니다.** 새 주로 넘어가면 화면은 항상 빈 상태로
   시작하고, 어느 한 주에서 내용을 새로 만들거나 고쳐도 다른 주의 기록에는 전혀 영향을
   주지 않습니다 — 예전처럼 모든 주가 같은 목록을 자동으로 공유하지 않습니다.
6. **"차주"에 적은 계획은 다음 주로 넘어갈 때(아래 "지난 주 내용 가져오기") 그 다음 주의
   "금주" 칸으로 한 번만 자동으로 옮겨집니다.** 실시간으로 같은 값을 계속 물고 있는 연동이
   아니라, 가져오기를 누르는 순간의 값을 그대로 한 번 복사해오는 방식입니다. 그래서:
   - 다음 주로 넘어간 뒤 그 주의 "금주" 내용을 고쳐도 지난 주의 "차주"는 전혀 바뀌지
     않습니다(한쪽 방향으로만 흐릅니다).
   - 이미 가져오기를 한 뒤에 지난 주의 "차주"를 또 고쳐도, 이미 복사되어 있는 다음 주의
     "금주"가 저절로 다시 바뀌지는 않습니다(그 시점에 다시 "가져오기"를 눌러야 최신 값이
     새로 복사됩니다).
   - "차주"는 새 주에서는 항상 빈 칸으로 시작합니다(그 주의 차주는 아직 계획하지 않은
     것이므로).
   - 담당자도 가져오기 시점에 함께 복사되어 넘어갑니다(다음 주에서 바로 수정 가능).
7. 내용이 전주와 크게 다르지 않을 때는, 주차 이동 옆의 **"◀ 지난 주 내용 가져오기"**
   버튼을 누르세요. 이 버튼을 누르는 순간 **지난 주의 분류·항목이 완전히 새로운 복사본으로
   이번 주에 생성**되고, 위 6번의 규칙대로 "차주" → "금주"가 함께 옮겨집니다(버튼을 누르기
   전에는 이번 주가 비어 있는 그대로 유지됩니다). 복사는 그 순간의 스냅샷이라서, 이후 이번
   주 내용을 수정하거나 삭제해도 지난 주의 원본 기록은 전혀 바뀌지 않습니다. 이미 이번
   주에 작성해둔 내용이 있는 상태에서 가져오기를 누르면, 지난 주 내용이 별도로 추가되며
   기존 내용은 지워지지 않습니다.
8. **엑셀로 내보내기**: 프로젝트 추가 버튼 옆의 **"⇩ 엑셀로 내보내기"**를 누르면 현재
   선택한 팀의 전체 기간 기록을 `.xlsx` 파일로 내려받습니다. 파일 안에는 **주차마다
   별도의 시트**가 생성되고(시트 이름 = `2026-W38`처럼 연도-주차), 각 시트는 화면과
   동일하게 분류/항목/금주/차주/담당자 순서에 분류 셀이 세로 병합된 표 형태입니다.
   파일명은 `주간보고_{팀이름}_{다운로드날짜}.xlsx` 형식입니다.
8. **지시사항 탭**: 상단 탭에서 "지시사항"을 누르면 별도 화면으로 전환됩니다(영업기획팀/
   영업관리팀 구분 없이 표 하나에서 전체를 관리하며, 담당팀은 필터 대상입니다).
   - **"+ 지시사항 추가"**를 누르면 지시 날짜·이행예정 날짜·지시사항 내용·담당팀·담당자·
     진행상태를 입력하는 창이 뜹니다. 지시 날짜와 지시사항 내용은 필수 입력입니다.
   - 표의 각 열 제목(지시 날짜, 이행예정 날짜, 지시사항, 담당팀, 담당자, 진행상태)을
     클릭하면 그 기준으로 오름차순/내림차순 정렬됩니다. 같은 열을 다시 클릭하면 방향이
     바뀝니다.
   - 기본 정렬(열 제목을 아직 클릭하지 않은 상태)은 **"진행 중" 상태의 지시사항이 맨
     위로 오고, 그 안에서는 지시 날짜가 최근인 순서**로 나열됩니다.
   - 진행상태 칸은 그 자리에서 바로 드롭다운으로 바꿀 수 있어(진행 전 → 진행 중 → 완료),
     매번 편집 창을 열지 않아도 상태만 빠르게 갱신할 수 있습니다.
   - 상단 필터 바에서 담당팀, 진행상태, 검색어(지시사항 내용·담당자 대상)로 원하는
     항목만 걸러볼 수 있고, "필터 초기화"로 한 번에 되돌릴 수 있습니다.
   - 이행예정 날짜가 오늘보다 지났는데 아직 "완료"가 아닌 항목은 날짜가 빨간색으로
     강조되어 기한 초과를 바로 알아볼 수 있습니다.
   - 각 행의 "편집"/"삭제" 버튼으로 내용을 고치거나 지울 수 있습니다.

여러 기기(사무실 PC, 집, 휴대폰 크롬 등)에서 같은 주소로 로그인하면 Firestore를 통해
실시간으로 같은 데이터가 동기화됩니다.

9. **표 디자인 개선(2026-09-19)**:
   - 주간보고 표의 구분선(칸을 나누는 선)을 더 진한 회색으로 바꿔서 칸 경계가 눈에 잘
     띄도록 했습니다.
   - 화면 좌우 여백을 줄이기 위해 표 전체 너비를 약간 넓혔습니다(비율이 어색해지지 않는
     선에서 적당히만 늘린 정도입니다).
   - **표 열 너비 직접 조절**: 각 열 제목(분류/항목/금주/차주/담당자) 오른쪽 끝에 마우스를
     올리면 커서가 열 너비 조절 모양(↔)으로 바뀝니다. 이 지점을 눌러서 좌우로 드래그하면
     그 열의 너비를 원하는 만큼 넓히거나 좁힐 수 있습니다. 예를 들어 담당자를 두 명 이상
     적어서 이름이 잘리거나, 항목/분류 내용이 길어서 두 줄로 넘어갈 때 해당 열을 넓혀서
     한눈에 보이게 만들 수 있습니다. 조절한 너비는 **그 컴퓨터의 그 브라우저에만 저장**됩니다
     (로그인 계정이 아니라 브라우저 자체에 저장되는 개인 설정입니다) — 새로고침하거나 나중에
     다시 접속해도 유지되지만, 다른 팀원의 화면이나 다른 컴퓨터/브라우저에는 영향을 주지
     않으며 Firestore 데이터에도 저장되지 않습니다. 지시사항 탭의 표는 이 기능과 무관하게
     기존 그대로입니다.

## 데이터 용량은 충분한가? (1년치만 남기고 자동 삭제할 필요가 있을까?)

**결론: 자동 삭제 없이 그냥 계속 쌓아도 무료 플랜 용량으로 수십 년치가 넉넉합니다.**
1년 지난 자료를 굳이 지우도록 만들 필요는 없다고 권장합니다. 이유는 다음과 같습니다.

- 이 앱이 저장하는 데이터는 전부 **글자(텍스트)** 뿐입니다 (분류명, 항목명, 상세설명,
  작성자, 날짜). 이미지·첨부파일이 없습니다.
- 상세설명 한 건은 길게 써도 보통 수백~수천 자 수준이고, Firestore 문서 하나는 이 정도
  글자 수 기준으로 대략 1~2KB 정도입니다. 영업기획팀·영업관리팀 두 팀이 각각 주당
  10~20개 항목을 작성한다고 가정해도 **한 주에 대략 50~100KB 이내**입니다.
- Firebase 무료(Spark) 플랜의 Firestore 저장 용량 한도는 **1GiB**입니다. 위 추정치로
  계산하면 1GiB를 채우는 데 약 **1만~2만 주(즉 190~380년)**가 걸리는 양입니다. 문서
  이름·타임스탬프 등 부가 정보를 넉넉히 얹어 계산해도 최소 수십 년 이상은 자동 삭제 없이
  버틸 수 있는 여유입니다.
- 읽기/쓰기 횟수 한도(일일 무료 한도: 읽기 5만 회, 쓰기 2만 회)도 팀 내부 사용 규모에서는
  거의 소진될 일이 없습니다.
- 오히려 지난 주간보고는 **분기·반기 실적 리뷰, 전년 대비 비교, 감사 대응** 등에 참고
  자료로 다시 쓰일 가능성이 높은 데이터라서, 용량 문제가 없다면 남겨두는 편이
  실무적으로 더 유리합니다.

정리하면 저장 용량이 부족해질 걱정 때문에 1년 후 자동 삭제 로직을 넣을 필요는 없고,
현재 구현대로 무기한 보관하는 것을 권장합니다. 다만 혹시 회사 문서 보존 정책상
"N년 이후 기록은 삭제해야 한다"는 규정이 별도로 있다면, 그건 용량 문제가 아니라
정책 준수 문제이니 필요 시 말씀해주시면 (예: "3년 지난 주는 목록에서 숨김/삭제") 별도
기능으로 추가해 드릴 수 있습니다.

## 참고 / 주의사항

- Firebase 무료(Spark) 플랜은 읽기/쓰기 횟수와 저장 용량에 여유로운 무료 한도가 있어 팀 내부용
  사용량으로는 사실상 비용이 발생하지 않습니다. (자세한 계산은 위 "데이터 용량은 충분한가?" 참고)
- 로그인 계정의 이메일/비밀번호는 곧 데이터에 대한 접근권한이므로 팀 내에서만 안전하게 공유하세요.
- 별도 자동 백업은 없으므로, 중요한 내용은 위 "엑셀로 내보내기" 기능이나 Firebase 콘솔의
  Firestore 데이터 내보내기(Export)로 주기적으로 백업하는 것을 권장합니다.

  값이 정확한지, 1-2단계 보안 규칙이 게시되었는지 확인하세요.
- 로그인 자체가 "이메일 또는 비밀번호를 확인하세요" 오류로 실패하면 → 1-3단계에서 이메일/비밀번호
  로그인 방식을 켰는지, 사용자 계정을 만들었는지 확인하세요.
- GitHub Pages 주소에서 로그인이 계속 실패하면 → 2-2단계의 승인된 도메인에 `.github.io` 주소를
  등록했는지 확인하세요.
- "엑셀 내보내기 중 오류가 발생했습니다"가 뜨면 → 최신 `app.js`(2026-09-18 이후 배포본)로
  교체했는지 확인하세요. 예전 버전에서 만든 분류/항목 문서 중 `week` 값이 없는 것이 섞여
  있어도 최신 버전은 이를 "미지정" 시트로 자동으로 묶어서 내보내므로 오류 없이 진행됩니다.
- 지시사항이나 식당을 저장할 때 **"저장 중 오류가 발생했습니다: Missing or insufficient
  permissions."**가 뜨면 → Firestore 보안 규칙이 아직 옛날 버전(`directives`나 `restaurants`
  컬렉션이 생기기 전의 규칙)으로 게시되어 있는 것입니다. Firebase 콘솔 > Firestore Database >
  **규칙(Rules)** 탭으로 가서, 이 프로젝트의 최신 `firestore.rules` 파일 내용(위 1-2단계
  코드 블록, `directives`와 `restaurants` 항목 포함)을 그대로 붙여넣고 다시 **"게시(Publish)"**
  하면 해결됩니다. 코드 자체의 문제가 아니라, 브라우저에 배포된 파일과 Firebase 콘솔에 게시된
  보안 규칙이 서로 다른 버전이라서 생기는 문제이니 두 곳을 항상 같이 업데이트해야 합니다.
- 지시사항을 편집·저장했는데(오류 문구 없이 창은 닫힘) 화면에는 바로 반영되지 않고,
  **페이지를 새로고침(F5)해야만 수정 내용이 보이는 경우** → 2026-09-19 이전 버전의 `app.js`에
  있던 버그입니다. 주간보고 탭에서 팀을 바꾸거나 주차를 이동하면 그 김에 지시사항 목록의
  실시간 연결까지 함께 끊겨버리고 다시 연결되지 않는 문제가 있었습니다(저장 자체는 정상
  처리되어 데이터는 안전하지만, 화면 갱신만 멈추는 문제). 최신 `app.js`로 교체하면 주간보고
  탭에서 팀/주차를 아무리 이동해도 지시사항 탭의 실시간 갱신이 끊기지 않습니다.
